What we are trying to achieve

STARS exists to make class attendance at MUT trustworthy and simple — for students who check in, for staff who run classes, and for leaders who need accurate reports without chasing paper registers.

1

Fair attendance

Students prove they are in the right place at the right time — not just asking a friend to sign a sheet. Short codes, location checks, and quick on-screen challenges reduce “proxy” signing.

2

Less admin for lecturers

Lecturers and tutors start a class session on their phone; students check in during that window. Registers and history build automatically instead of manual tallies after every class.

3

Clear visibility for leadership

Deans, HODs, and administrators see attendance patterns for their faculty or department — not the whole university unless their role allows it. Decisions are based on live data, not outdated spreadsheets.

4

One system, many roles

The same app serves students, lecturers, tutors, and management — each person only sees what their job requires. That keeps privacy and responsibility aligned with MUT’s structure.

The problem today

  • Paper registers are easy to lose, slow to summarise, and hard to audit.
  • Manual sign-in does not prove the student was actually in class.
  • Faculty and central offices wait weeks for attendance figures that may already be out of date.
  • Different modules and campuses use inconsistent processes.

What success looks like

When STARS is fully rolled out, a typical class looks like this:

  1. Lecturer starts class — opens STARS, starts an attendance session for that module (often with a location boundary around campus or the venue).
  2. Students check in — enter the session code or follow the on-screen steps; the app confirms they are eligible and present.
  3. Record is saved — attendance is stored securely; students can view their own history; lecturers can close the session and produce a register.
  4. Leaders review trends — authorised staff see summaries for their scope (module, department, or faculty) without accessing unrelated personal data.

Where we are now (honest picture)

The app screens and user journeys are largely built — students, lecturers, and leadership dashboards exist and can be demonstrated. The team is now connecting the app to a secure online database so data is real, shared, and backed up — not only stored temporarily for demos on a single device.

Until that connection is finished, some demonstrations use sample data so the Innovation Lab can show flows and gather feedback. That is normal in product development: experience first, then live data.

In one sentence: We are building STARS so MUT can run modern, fair attendance — on phones students already carry — with reports leaders can trust.

What is STARS?

Project overview

STARS replaces paper registers and ad-hoc check-ins with a single app: students mark attendance via session codes and challenge verification; lecturers and tutors run live sessions with GPS bounds; deans, HODs, and admins see scoped analytics. The UI and navigation are largely complete in the Expo repo — the current phase connects real identity and data through Supabase without rewriting screens.

Who uses it

StudentDashboard, join modules, mark attendance, challenge check-in, history
Lecturer / tutorCreate sessions, rotating codes, class registers, module hub
HOD / Dean / AdminFaculty- or university-scoped analytics, audit logs, governance views

How we build & run

Process

1. Local setup

cd ATTANDANCE
npm install
npx expo start -c
  • Use npx expo start, then Expo Go (device) or w for web.
  • Web favicon: public/favicon.svg at /favicon.svg; app/+html.tsx sets title and meta; app.json → expo.web.favicon for export.
  • SEO (web): No separate public/index.html (breaks SPA routing). app/+html.tsx provides description, OG, Twitter Card, robots, theme-color; optional EXPO_PUBLIC_SITE_URL for canonical when deployed.

2. Architecture principles

  1. Repository-style services — mockDB mimics collections; attendanceSimulationService and moduleEnrollmentService sit above it so Supabase replaces storage without rewriting screens.
  2. Role-based routes — /admin/*, /dean/*, /hod/*, /lecturer/*, /tutor/*, /student/*, plus /notifications, /settings. See INSTITUTION_HIERARCHY.md in the repo.
  3. Route groups — (auth) organizes files only; URLs are /onboarding, /login, /register-student (parentheses are not in the path).
  4. UI system — ScreenShell + tokens in src/theme/; Innovation Lab footer pinned below scroll content.

2.1 DRY rules

  • Screens are thin — data fetching and writes live in src/services/.
  • One component per concept — shared UI is parameterized, not copied.
  • One helper per repeated rule — validation/formatting in src/utils/.
  • Offline-first mindset — actions enqueue mutations that retry; do not block UX on network.

2.2 Offline-first + sync (PouchDB)

PathPurpose
src/services/offline/pouchDb.tsPouchDB config (AsyncStorage / IndexedDB) + doc types
src/services/offline/offlineRepository.tsGeneric upsert/get/list — no business logic
src/services/offline/offlineSync.tsMutation outbox + background push to Supabase

Pattern: service writes to PouchDB (offline UI) → enqueues mutation → background sync marks acked or failed for retry.

Structure

Architecture (layers)

app/ screens ← role routes (student · lecturer · admin · dean · hod) src/components/ ← UI shell, charts, challenge grid src/services/ ← business logic; mock vs supabase branch src/services/supabase/← repositories (Auth, Postgres) src/mockDB/ ← JSON seeds (mock mode only) src/pipelines/ ← multi-step flows (auth hydration, register) supabase/migrations/ ← schema, RLS, Edge Functions
Golden rule (integration): screens import src/services/ only — never the Supabase client directly in app/.
Core product flow

Attendance (mock today)

  1. Lecturer, tutor, or delegated registrar starts a session → one GPS read → row records startedByRole, startedById, algorithmSeed, expiry.
  2. Rotating 6-digit code (and QR) derived locally from seed + 5s window — no per-tick DB writes.
  3. Student submits code → GPS read → Haversine vs session radius → record in mock DB (Postgres when integrated).
  4. Challenge path (M6): visual gate + attendance_records with device id, time bucket, GPS hash, tapped index — see full-challenge-mechanism.md in repo.

Support

Troubleshooting

  • Metro / Node issues — Node 20 LTS; delete node_modules; reinstall.
  • Expo Go stuck on “Loading your space…” — verify app.json assets; npx expo start -c --lan; try hotspot if campus Wi‑Fi blocks devices.
  • NativeWind preset error — tailwind.config.js must include presets: [require("nativewind/preset")].
  • SecureStore on web — use src/utils/authStorage.ts (wired in authStore).
